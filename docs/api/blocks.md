# User blocks API

Личный чёрный список закрывает **новые** совместные поездки. Запись направлена
(`blocker → blocked`), чтобы пользователь мог удалить только свою блокировку,
но travel-эффект взаимный: пара закрыта при строке в любую сторону.

Все endpoints требуют user Bearer JWT. Заблокированной стороне отдельное
уведомление не отправляется, а API не раскрывает `blockedByOther`.

## Endpoints

### `GET /api/v1/blocks?page=1&limit=20`

Возвращает только список текущего пользователя, новые записи первыми:

```json
{
  "items": [
    {
      "user": { "id": "...", "name": "...", "avatar": "..." },
      "blockedAt": "2026-10-23T18:00:00.000Z"
    }
  ],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 1,
    "totalPages": 1,
    "hasMore": false
  }
}
```

`limit`: 1..50, `page`: 1..10000.

### `GET /api/v1/blocks/:userId`

Возвращает только собственную направленную запись:

```json
{ "blockedByMe": true }
```

`false` не означает, что встречной блокировки нет.

### `PUT /api/v1/blocks/:userId`

Идемпотентно создаёт блокировку и возвращает `BlockedUserItem`. Блокировка
себя → `400 VALIDATION_FAILED`, неизвестная/удалённая цель → `404 NOT_FOUND`.

### `DELETE /api/v1/blocks/:userId`

Идемпотентно удаляет только запись текущего пользователя:

```json
{ "success": true }
```

Если встречная сторона тоже создала блокировку, mutual travel-гейт остаётся.

## Влияние на поездки

- `GET /trips` исключает поездки пары и считает `pagination.total` после фильтра;
- `GET /trips/:id` возвращает 404, чтобы не служить оракулом;
- `POST /bookings` возвращает 404 до изменения места;
- ride-request feed/matching и match-уведомления исключают пару;
- существующие pending/confirmed брони, собственные поездки и архивная история
  остаются доступны для исполнения обязательств, отмены, жалобы и отзыва;
- admin API не фильтруется.

После реального изменения обе стороны получают непрозрачный WS hint
`visibility:changed` без actor id, inbox, Telegram-сообщения или toast.
